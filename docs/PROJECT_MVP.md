应用核心功能描述

应用首先会收集和展示一些具有代表性的流行歌曲排行榜视频，例如“80年代大陆经典歌曲Top 100”“90年代内地流行金曲Top 100”“某年度十大金曲”等。系统利用AI从这些视频中提取歌曲排行榜，把原来只能“看视频”的内容转换成可以搜索、浏览和操作的文字列表，包括歌曲排名、歌名、歌手、年代，以及原始视频来源。

用户看到这个文字排行榜以后，可以通过点击、文字输入或者语音输入表达自己的偏好。例如用户可以说：“我最喜欢这里面的《大海》《弯弯的月亮》《涛声依旧》……”或者直接说：“把这10首作为我的90年代Top 10。”系统就会生成用户自己的相对排行榜。

这里的重点不是要求用户把100首歌全部重新排名，而是允许用户非常自然地逐渐形成自己的榜单。例如用户可以从Top 100中选20首，再从20首中形成Top 10；也可以通过简单的比较方式，例如：

“《涛声依旧》和《弯弯的月亮》，你更喜欢哪一首？”

通过几次选择，AI逐步帮助用户形成个人排行榜。

另外，系统提供一个非常简单的 My Singing List / 我的演唱曲目。用户可以把任何一首歌曲加入自己的演唱列表，例如：

会唱 / 正在练 / 想学 / 常唱

这样，一首歌实际上可以同时有两种身份：它既可能是用户非常喜欢的歌曲，也可能是用户正在学习演唱的歌曲。# 中国大陆流行歌曲榜单与个人演唱曲目库 MVP

## 1. 产品定义

将中国大陆流行歌曲排行榜视频转换为可浏览的文字榜单，并让用户从中建立自己的歌曲偏好榜单和演唱曲目库。

一句话描述：**把“看排行榜视频找歌”变成“浏览可操作的歌单，建立自己的 Top 榜与演唱清单”。**

首版服务于喜爱中国大陆经典流行音乐、希望系统地找歌与管理练唱曲目的个人用户。内容优先覆盖 1980 年代至今的大陆原创流行音乐；每个榜单必须保留来源，避免将非权威整理误作官方排行。

## 2. 要解决的问题

排行榜视频中的歌名、排名和歌手通常只能在画面中浏览，存在三个直接问题：

1. 用户难以搜索、筛选或保存视频中的歌曲。
2. 用户想从一长串经典歌曲中选出自己的前十，缺少轻量的排序方式。
3. 用户的“会唱、常唱、正在练、想学”曲目分散在记忆或聊天记录中，不能持续管理。

## 3. MVP 目标与边界

### 产品目标

- 为用户提供一批经过人工审核的公开歌曲榜单。
- 将榜单以结构化列表呈现：排名、歌名、歌手、年代、来源。
- 让用户从榜单中快速生成和维护个人 Top 10。
- 让用户维护自己的演唱曲目及练习状态。

### 非目标

MVP 不提供完整歌曲播放、音频下载、歌词展示、社交动态、公开用户榜单、自动推荐流、订阅付费或复杂声乐评测。用户可通过原始视频链接回到来源平台；产品不托管受版权保护的音视频内容。

## 4. 核心用户与使用场景

| 用户 | 主要需求 | 完成标志 |
| --- | --- | --- |
| 怀旧听歌者 | 按年代寻找大陆经典歌曲 | 找到并收藏感兴趣的歌曲 |
| 练唱用户 | 管理会唱、在练和想学的曲目 | 能查看下一首要练的歌 |
| 歌曲研究者 | 追溯歌曲在某个榜单中的来源 | 能看到原视频及榜单性质 |

典型路径：用户打开“90 年代大陆流行歌曲总榜”，浏览前 100 首，选中 10 首建立“我的 90 年代 Top 10”，再把其中几首标为“正在练”或“常唱”。

## 5. MVP 功能需求

### 5.1 榜单发现与浏览

- 首页按年代展示已发布榜单，例如 1980s、1990s、2000s、2010s、2020s。
- 榜单详情显示名称、适用年代、歌曲数量、来源性质、原视频链接、整理说明和最近核验时间。
- 用户可按歌名或歌手搜索当前榜单，并按排名顺序浏览。
- 每条歌曲至少显示：排名、歌名、歌手、所属年代；未核实字段明确标注“待核实”。

首版初始内容建议只上线 3 个质量可控的榜单：1980 年代大陆代表歌曲、1990 年代内地流行歌曲、1993 年起《中国歌曲排行榜》年度金曲。每个榜单先收录 20–100 首已审核条目，宁缺毋滥。

### 5.2 榜单录入与审核（运营后台）

榜单不会在 MVP 中对普通用户开放自动抓取。运营人员提交视频 URL 与榜单元数据，系统调用 AI 提取候选条目，再由人工确认后发布。

- 输入：视频 URL、榜单名称、年代范围、来源说明、榜单性质（官方评选 / 媒体榜单 / 民间整理）。
- AI 输出候选的排名、歌名、歌手及画面时间点。
- 审核员逐条确认、修改或删除，并可标记“待核实”。
- 只有审核完成的榜单可以在前台展示。

这样既保留 AI 提效，也避免因 OCR、字幕或视频剪辑错误直接污染公共数据。

### 5.3 我的 Top 榜

- 用户可从任意公共榜单将歌曲加入“我的榜单”。
- 首版只支持一个默认榜单“我的 Top 10”，最多 10 首。
- 用户可添加、移除、拖拽排序；若已满 10 首，先移除或替换已有歌曲。
- 用户也可通过文字输入添加歌曲；未匹配公共曲库时，显示“待确认歌曲”，不自动创建正式曲目。

语音输入作为可选增强：用户说出“把《大海》加入我的 Top 10”，客户端先转文字，再走与文字相同的歌曲匹配与确认流程。它不影响首版主流程的可用性。

### 5.4 我的演唱曲目

- 用户可从公共榜单、个人 Top 榜或搜索结果加入“我的演唱曲目”。
- 每首歌只有一个当前状态：`会唱`、`常唱`、`正在练`、`想学`。
- 用户可更新状态、添加简短备注，并按状态筛选。
- 同一首歌曲可同时存在于“我的 Top 10”和“我的演唱曲目”。两者独立：移出 Top 10 不影响演唱状态。

## 6. 页面与关键流程

| 页面 | 用户动作 | 结果 |
| --- | --- | --- |
| 榜单首页 | 选择年代或搜索歌曲/歌手 | 进入匹配的榜单或歌曲结果 |
| 榜单详情 | 浏览、搜索、点选歌曲 | 加入 Top 10 或演唱曲目 |
| 我的 Top 10 | 添加、替换、拖拽排序 | 保存个人偏好顺序 |
| 我的演唱曲目 | 设置状态、备注、筛选 | 形成可持续维护的练唱清单 |
| 登录 / 首次使用 | 使用手机号或邮箱登录 | 建立可跨设备保存的个人数据 |

关键操作采用显式确认：当语音或文字匹配到歌曲时，先展示“歌名 + 歌手”，用户确认后才写入个人列表。这可以处理同名歌曲和语音识别误差。

## 7. 数据模型（最小集合）

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `Song` | id、title、artist、release_year、verified | 规范歌曲记录；年份未知时为空 |
| `Ranking` | id、title、era、source_type、source_url、description、published_at | 一个可浏览的公开榜单 |
| `RankingEntry` | ranking_id、song_id、rank、source_timestamp、verification_status | 歌曲在榜单中的位置及可追溯证据 |
| `User` | id、login_identifier、created_at | 登录用户 |
| `UserTopListEntry` | user_id、song_id、position | 用户 Top 10，position 唯一且为 1–10 |
| `SingingListEntry` | user_id、song_id、status、note、updated_at | 用户的演唱曲目状态 |

`source_type` 必须区分“官方评选”“媒体榜单”“民间整理”。`verification_status` 至少包括“已核实”和“待核实”。

## 8. 实现方案

采用一个前后端分离的 Web 应用即可满足 MVP：

- 前端：响应式 Web 页面，优先支持手机浏览与单手操作。
- 后端 API：用户、榜单、歌曲、个人榜单、演唱曲目的读写接口。
- 数据库：关系型数据库，保障歌曲、榜单和个人条目的去重及关联完整性。
- 运营工具：受权限保护的简单后台，用于录入视频、审核 AI 提取结果和发布榜单。
- AI 管道：对视频字幕、描述或抽帧 OCR 生成候选条目；结果始终进入人工审核队列。

第一阶段可直接人工录入与审核 3 个榜单，AI 提取管道可在第二个迭代上线。这样先验证用户是否愿意保存和管理歌曲，避免把主要开发时间投入不确定的视频提取准确率。

## 9. 验收标准

MVP 可上线的最低标准：

1. 前台至少有 3 个已发布的大陆歌曲榜单，总计不少于 60 条审核过的歌曲记录。
2. 每个公开榜单都显示可访问的来源链接及榜单性质。
3. 用户能在一个榜单内按歌名或歌手搜索，并把歌曲加入或移出个人 Top 10。
4. 用户能调整 Top 10 的 1–10 顺序，刷新或重新登录后顺序仍正确。
5. 用户能添加歌曲到演唱曲目，并在四种状态之间切换和按状态筛选。
6. 重复添加同一歌曲不会产生重复的个人曲目；同名不同歌手歌曲必须由用户确认。
7. 未核实的年份、歌手或排名不会被伪装成确定数据。

## 10. 开发顺序

| 阶段 | 交付内容 | 完成判断 |
| --- | --- | --- |
| 0：内容准备 | 选定 3 个来源、建立歌曲规范和人工审核表 | 有至少 60 条可追溯条目 |
| 1：核心产品 | 榜单浏览、搜索、登录、Top 10、演唱曲目 | 验收标准 2–6 通过 |
| 2：内容提效 | 运营后台、AI 提取候选、审核发布 | 新视频可在后台完成录入与审核 |
| 3：体验增强 | 语音输入、更多榜单和筛选 | 语音匹配经确认后正确入库 |

## 11. 成功指标

上线后先观察四个指标，而不急于扩张内容规模：

- 激活：新用户中完成“加入第一首演唱曲目”的比例。
- 核心价值：新用户中完成“我的 Top 10”的比例。
- 留存：7 天内至少再次更新一次演唱状态的用户比例。
- 内容质量：已发布榜单中被用户报告错误的条目占比。

## 12. 已知风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 视频中的排行榜并非权威来源 | 明示来源性质和链接，不把民间整理称为官方榜单 |
| AI 错读歌名、歌手或排名 | AI 只生成候选，发布前人工审核；保留视频时间点 |
| 音视频版权问题 | 不存储或播放完整音视频，只展示来源链接和结构化元数据 |
| 同名歌曲、翻唱版本混淆 | 以歌名 + 歌手作为展示与确认单位，允许标记待核实 |
| 语音识别不稳定 | 语音仅作文字输入入口，写入前要求用户确认匹配结果 |

## 13. 下一步决策

开始开发前只需确认以下三项：

1. 首批三个榜单的具体来源视频与可使用的链接。
2. 首版登录方式：手机号验证码或邮箱验证码。
3. 是否把“语音输入”纳入第一期；若无法确定，默认放入第二期。
